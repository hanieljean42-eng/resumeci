I. Pourquoi les XSD remplacent les DTD

Limite de la DTDApport du XSD
Pas au format XML → outil de parsing spécialÉcrit en XML → mêmes outils
Ne supporte pas les namespacesGère les espaces de noms
Typage très limité (#PCDATA, #CDATA)~40 types de données + types personnalisés
Historique : W3C, février 2000. Objectif : remplacer la DTD. Avantages : extensible (nouveaux types), éléments de même nom au contenu différent, occurrences précises (minOccurs/maxOccurs), héritage (extension).

II. Structure de base

<?xml version="1.0"?>
<xsd:schema xmlns:xsd="http://www.w3.org/2001/XMLSchema">
  <!-- déclarations d'éléments, attributs et types -->
</xsd:schema>
  • Racine : <xsd:schema> ; tout élément du schéma est préfixé xsd: ou xs: ;
  • xmlns:xsd="http://www.w3.org/2001/XMLSchema" déclare l'espace de noms des types XSD ;
  • xmlns="..." (sans préfixe) = espace de noms par défaut.

III. Référencer un schéma depuis un document XML

<livre xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:noNamespaceSchemaLocation="schema.xsd"> ... </livre>
  • xmlns:xsi : déclare l'espace de noms de l'instance ;
  • xsi:noNamespaceSchemaLocation : localisation du .xsd sans namespace ; xsi:schemaLocation : utilisé quand il y a un namespace.

IV. Déclaration d'éléments et d'attributs

<xsd:element name="nom" type="type" minOccurs="0" maxOccurs="unbounded"/>
  • type : type simple prédéfini (xsd:string, xsd:integer, xsd:decimal, xsd:date, xsd:year, xsd:boolean…) ou type complexe utilisateur ;
  • minOccurs/maxOccurs : nombre d'occurrences — "unbounded" = illimité ;
  • Un élément peut contenir une déclaration inline <xsd:complexType> avec <xsd:sequence> (ordre), <xsd:choice> (alternative), <xsd:all>.
<xsd:attribute name="isbn" type="xsd:string" use="required" default="..."/>
  • use : required (obligatoire), optional/implied (optionnel), fixed (valeur fixe) ;
  • default/fixed : valeur par défaut.

V. Types de données et restrictions

Types simples intégrés

Près de 40 types : string, integer, decimal, float, boolean, date, year, CDATA… Utilisation : type="xsd:integer".

Restriction d'un type intégré

<xsd:simpleType name="typeISBN">
  <xsd:restriction base="xsd:string">
    <xsd:pattern value="[0-9]{10}"/>
  </xsd:restriction>
</xsd:simpleType>
  • base : type dont on dérive (ex. restreindre xsd:string) ;
  • <xsd:pattern> : expression régulière (ISBN = 10 chiffres) ;
  • Autres : <xsd:minInclusive>, <xsd:maxInclusive>, <xsd:enumeration>, <xsd:length>…

Type complexe

<xsd:complexType name="typePages"> ... </xsd:complexType>

Définit un élément avec sous-éléments et/ou attributs. <xsd:simpleContent> + <xsd:extension base="xsd:string"> = élément textuel portant des attributs (ex. titre avec attribut langue).

VII. Exemple type (sujet d'examen)

  • etudiant : attribut id type ID ; annee = entier ;
  • inscription : attributs etudiant/cours en IDREF ; note décimal 0-20 ; session énumération (normale|rattrapage).

VIII. ⚠️ Pièges d'examen

⚠️ Pièges classiques :
  • Oublier le préfixe xsd: sur les balises du schéma.
  • Confondre noNamespaceSchemaLocation (sans namespace) et schemaLocation (avec namespace).
  • Mettre maxOccurs="unbounded" sans minOccurs → minOccurs par défaut = 1 ; pour « 0 ou plus » il faut minOccurs="0" aussi.
  • Oublier que use="implied" = optionnel (équivalent DTD #IMPLIED).
  • Déclarer un type complexe pour un élément sans sous-éléments → utiliser simpleType à la place.
  • Dans une restriction, oublier base="..." : on ne restreint pas « dans le vide ».
